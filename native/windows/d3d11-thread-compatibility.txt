WineD3D native Windows context and driver boundaries (0.9 investigation)
======================================================================

Confirmed failure and scope
---------------------------
Astalon 1.1.0 (x86 Unity 2019.4.13) crashes when the native-host Wine
OpenGL renderer runs with WINE_D3D_CONFIG=renderer=gl,csmt=0. The first
thread's texture upload succeeds. A subsequent application thread creates
another shared WGL context, which fails while the original context remains
current on the first thread. Wine then dereferences the missing context in
wined3d_texture_gl_prepare_texture (0.8 x86 wined3d RVA 0xce173).

The independent fixture reproduces this on both actual GL renderers:
  NVIDIA GeForce RTX 4090: GetLastError 0xc00710dd, low Win32 code 4317
                          ERROR_INVALID_OPERATION (not HRESULT_FROM_WIN32).
  Intel UHD Graphics 770: GetLastError 0xaa, ERROR_BUSY.

Temporarily unbinding the first context in the fixture makes all operations
pass using unchanged 0.8 DLLs. This is a diagnostic control, not the normal
passing test path and not an application workaround required by the fix.

Implementation
--------------
dlls/wined3d/context_gl.c and wined3d_gl.h cache release_on_exit per context
only when the actual command stream has no worker thread and native ntdll
does not export wine_get_version. At the outermost release of the currently
owned context, the existing set_current(NULL) path flushes commands and
clears both native WGL and Wine TLS/current state. Nested acquisitions,
restored foreign application GL contexts, and delayed/destroyed contexts
retain their existing handling. Asynchronous CSMT and ordinary Wine ntdll
paths keep the previous behavior.

Native synchronous teardown uses glFinish on the context being destroyed,
instead of reacquiring a context after removing it from the device list.
Internally owned submitted fences are explicitly destroyed before deleting
their GL free list; caller-owned query fences retain their normal ownership.
The change deliberately does not turn a failed upload into silent success.

Fixture and commands
--------------------
  build-d3d11-texture-thread-probe.ps1
  d3d11-texture-thread-probe.cpp
  test-d3d11-texture-thread.ps1

Example (from repository root):
  & native/windows/build-d3d11-texture-thread-probe.ps1
  & native/windows/test-d3d11-texture-thread.ps1 `
      -RuntimeDirectory native/windows/test-output/runtime09-graphics `
      -Bits 32 -Preference discrete -Desktop -SwapChain

The discrete executable exports NvOptimusEnablement and
AmdPowerXpressRequestHighPerformance, matching Astalon. GL_RENDERER trace
proves the active backend; DXGI's reported adapter name alone is insufficient.
The fixture uses sequential same-device operations on the main thread, a
worker, a replacement worker after thread exit, and the main thread again.
It checks initial texture data, SRVs, exact staging pixels, bounded EVENT
query completion, worker-recorded deferred commands and full COM teardown.
An optional foreign-context case also checks HGLRC/HDC preservation across
device creation, texture upload/readback and destruction. No Present, input,
capture, original-game modifications or host display/audio changes occur.

Each child has a 45-second watchdog; query polling is bounded to 10 seconds.
The runner captures through gui-log-capture with a 16 MiB log cap and records
truncation metadata. It deliberately does not enable d3d_sync, which changes
Wine command-stream synchronization. Debug logging still affects timing;
these are correctness tests, not throughput measurements.

Earlier component-only limits and subsequent repairs
---------------------------------------------------
This establishes a synchronous WineD3D crash fix. Actual Astalon testing on
runtime09-graphics now survives the previous csmt=0 crash but still stalls
at the same six save-loading messages. It does not fix the default csmt=1
black startup; that mode passes this small fixture before and after patching.

NVIDIA foreign-GL creation of a second Wine D3D11 device hangs during adapter
caps initialization in both csmt modes. Native D3D11 controls pass. The same
hang is reproduced with unchanged 0.8 csmt=1, so it predates this patch:
  graphics-09/textures-76bbfca011744c1a8b28c73667819d1c/result.json
Candidate x86/x64 records (watchdog exit 124, not passing coverage):
  graphics-09/textures-093c65cc47f549a680c4c3863be3c718/result.json
  graphics-09/textures-9abebb4e38bf41749cb33438f5f30b74/result.json
The last trace shows Wine DXGID3D10CreateDevice(flags=0x9) on another thread
while the main thread is creating the native WGL caps context.

Actual Astalon default-mode diagnostics now prove the native driver enters
Wine's public D3D11CreateDevice first. The validated x86 frame-pointer chain,
NVIDIA call instruction and saved function pointer agree:
  graphics-09/astalon-48476-call-proof.json
  graphics-09/astalon-nvidia-callsite.txt
  graphics-09/astalon-48476-stacks.txt
The NVIDIA return address is nvoglv32+0x88a5cb; the indirect call target is
Wine d3d11+0x5870 (D3D11CreateDevice). That thread then waits in Wine's mutex;
Wine's command-stream worker is inside NVIDIA via glClientWaitSync. Native
DXGI is loaded alongside Wine DXGI, but no native D3D11 was loaded. WCT alone
did not report a cycle; the stronger evidence is the saved call/frame state.

The earlier native graphics routing covered only DXGI factory entrypoints.
Forwarding DXGID3D10CreateDevice based solely on its immediate caller would
miss this case, because its caller is already Wine D3D11. The new boundary in
dlls/d3d11/d3d11_main.c passes the original public-constructor caller to the
native shim. graphics-backend.cpp classifies genuine Windows module paths;
application / Wine callers retain the original Wine implementation. The
native constructor is loaded by a fixed system path, verified by backing-file
identity and retained for returned COM object lifetimes. Native failure is
final and never retries through Wine. No graphics APIs are selected merely
by DLL basename. Return-address tail-call ambiguity remains a known limit.

The first combined runtime09-driver advanced beyond the driver deadlock,
then exposed an existing display shim crash. Native EnumDisplaySettingsA
sets dmSize=124 and dmDriverExtra=0 before calling its extended API; the
wide variant sets188/0. The old shim bypassed that initialization. With a
driver's zero-sized input, native ExA computed an underflowed copy length
of0xffffffe0 and overwrote its stack. Offline proof:
  graphics-09/native-bridge-display-crash-proof.json
  graphics-09/native-enum-display-simple-a.txt
  graphics-09/native-enum-display-simple-w.txt
  graphics-09/native-enum-display-exa-copy.txt

display.cpp now preserves simple-API normalization and bounds virtual /
registry output copies to the supplied legacy/full DEVMODE size. Genuine
Windows EnumDisplaySettings and GetDeviceCaps callers query physical modes;
ordinary application / Wine queries retain virtual modes. Nested query scopes
restore their previous depth and application callbacks regain virtual query
behavior. ChangeDisplaySettings modeset safeguards remain unchanged.
